# Krono workspace consolidation

Krono's browser workspace uses the authenticated Fastify gateway, the private FastAPI product service, one PostgreSQL paper ledger, and an independent Python worker. This supersedes the multiple-workspace navigation in the original architecture audit. The inventory below is based on source and existing tests at `0cda2d4`.

## Migration order

1. Route the regular web build directly to the authenticated product workspace, with compatible redirects for product bookmarks and retired paths. Keep the legacy UI available only to the development regression fixture while tests are migrated.
2. Reuse the existing product components and add navigation in one shell. Use tenant data across Dashboard, Portfolio, Paper Trading and Agents. Move emergency actions to the same account that executes orders.
3. Strengthen the worker's pre-activation and periodic validation without adding another queue or ledger. Verify strategy pinning, retries, pause and restart behavior against PostgreSQL.
4. Review legacy-only capabilities against what the spot product can represent. Retain DEX state and transaction histories until ownership and units can be verified. If historical records are needed in the product, import them into a read-only provenance-preserving archive with record-count, balance and tenant-ownership reconciliation. Never add legacy simulation cash or DEX marks to a live paper account.
5. Retire old runtime entry points and tests only after each relevant workflow has been verified against the replacement. Unmapped chain operations remain operator-side. Deploy only with separate authorization.

The PostgreSQL runtime pins a saved strategy version and a reproducible backtest before activation. It uses durable leases, restart fencing, quote and exposure checks, and an idempotent execution gate. Natural-language authoring is model-assisted and validates its output against the same schema. It has no execution permission. Continuous rules and risk checks do not imply continuous LLM strategy optimization.

## Release and retirement boundaries

- Migration `0008_agent_replay_workflow.sql` backfills original report identities, preserves active pinned versions and initializes the next review timestamp for monitoring agents. Agent requests remain idempotent after the current report changes.
- The website gateway exposes product and auth operations. The former cloud runtime routes and the historical browser shell are registered in test configurations only. Existing remote jobs and local DEX archives require explicit operator inventory and reconciliation before retirement.
- The spot paper gate reuses the reviewed hourly and daily trade caps. Executed exits count toward the next entry’s frequency check, and entry caps leave exits available.
- Weekly replay updates the evidence for a pinned version and can fail the agent. It does not replace its strategy, move ledger balances, or trigger chain execution.
